# Android security

## Secure local state

SecureStorage 8.0.0 encrypts Android session data using Keystore-backed keys. Native calls have an eight-second deadline so two sequential startup reads and the biometric probe stay within the twenty-second startup budget. If the plugin is unavailable, tokens remain memory-only and the salted PIN verifier falls back to the app-private IndexedDB security store; neither path stores plaintext credentials. Web bypasses the native plugin completely and stores the PIN verifier directly in IndexedDB.

PIN protection is available on both Web and Android; biometric unlock is Android-only and always keeps the PIN as fallback. PIN verifier storage is chosen explicitly by platform, so the web app never probes native secure storage before falling back.

The PIN is numeric, 4–6 digits, confirmed on setup. A fresh 16-byte random salt and PBKDF2-SHA256 with 600,000 iterations derive a 256-bit verifier. The record stores algorithm version, iteration count, verifier, salt and throttle metadata. It never stores the PIN. Verification compares derived bytes without early exit.

After five failed attempts, retries pause for 30 seconds; repeated failures increase the delay to a five-minute cap. Retry state persists in secure storage across restarts. Successful PIN entry resets failure state. This is a local app-lock layer, not protection against a fully compromised device.

## Lock lifecycle

The app locks at cold launch and on native background/resume transitions. The protected shell removes its routed content when locked; there is no protected UI behind an unlock modal. A background transition during PIN derivation cannot finish by silently clearing a newer lock.

Biometric prompts are excluded from background events generated by the prompt itself. The Unlock screen offers biometrics once on entry and always retains a masked PIN fallback. Failed or cancelled biometrics do not unlock.

Enabling biometrics requires an enabled PIN, current PIN confirmation, enrolled strong biometric availability, and successful native authentication. Device credentials are not an alternate biometric fallback. PIN is the fallback if no enrollment remains. Changing or disabling PIN also disables biometric preference.

## Startup recovery

Startup never lets a local PIN, storage, or biometric problem trap an unauthenticated user: it fails closed to the Worker login screen rather than a blocking "could not finish starting" error, and it distinguishes a local security failure from a connection failure in the message shown. If a valid session exists but a configured protection record cannot be read or parsed, the app does not render protected content; it clears the unreadable record and requires Worker password reauthentication before continuing. Routing is deterministic (no valid session → login, valid session + locked → unlock, otherwise dashboard) and guards enforce the same rules for deep links.

## Native configuration

The Android patch disables Auto Backup and excludes cloud backup/device transfer of app data. Release cleartext HTTP is disabled. No unrelated runtime permissions are requested. Worker security remains server-side; backend credentials must never enter source or Android resources.

Capacitor uses `androidScheme: 'https'`, so the WebView origin is `https://localhost`. The Worker must allow this origin in its CORS policy (reflecting it in `Access-Control-Allow-Origin`, allowing the `Authorization` and `Content-Type` headers, and answering `OPTIONS` preflight for `/api/auth/*`). CORS is not loosened to `*` for authenticated requests. The Worker source is outside this repository; a CORS/origin rejection surfaces as a network error at login rather than a startup failure.

The maintained plugins selected for Capacitor 8 are [SecureStorage](https://github.com/aparajita/capacitor-secure-storage) 8.0.0 and [BiometricAuth](https://github.com/aparajita/capacitor-biometric-auth) 10.0.0.

## Device acceptance checks

After installing dependencies and generating Android:

1. Sign in with a valid Worker password. Cold-launch with no token, an expired token, a valid token, and a revoked token.
2. Interrupt network access during startup. Confirm protected content never flashes and retry works when connectivity returns.
3. Enable 4-, 5-, and 6-digit PINs; reject mismatches, letters and invalid lengths. Change and disable PIN only with correct current PIN.
4. Kill and relaunch the app, background/resume it, use Android Back, and deep-link to a protected route while locked. Confirm no protected content is accessible.
5. Fail PIN five times, restart during the delay, and confirm throttling persists. Wait and unlock correctly.
6. Enable biometrics after PIN confirmation. Exercise success, cancel, failure, removal of enrollment, unavailable hardware and PIN fallback.
7. Expire/revoke the Worker session while locked. PIN and biometrics must not restore backend authentication.
8. Sign out and relaunch; verify token removal and retained theme/security preferences.
9. Check launcher masks, light/dark splash surfaces, 168dp image scale, status/navigation bars, keyboard resize, and safe-area spacing on Android 12+ and a minimum-supported device.
10. Check 320px-wide web/phone, tablet and desktop layouts, 200% zoom, keyboard-only navigation and screen-reader labels. Run AXE on Login, Unlock, each list/detail, and Settings in both themes.
11. Verify APK installation, AAB acceptance, matching version metadata, signed-artifact labels and R8 mapping availability in CI.

These device and accessibility checks were not performed during implementation. The Windows environment cannot execute the WSL-managed Vitest/Rollup binary, and npm was unavailable in the noninteractive WSL shell. Dependencies were subsequently observed installed; Angular template and test-source type checks passed.
